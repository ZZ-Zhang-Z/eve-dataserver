## 1. 一分钟速览

**跑的是什么**：一个常驻控制器（`controller.py`）按调度表拉起采集子进程。控制器本身几乎不占内存，采集任务每次都是新进程，跑完即退。

**四个任务**：

| 任务 | 频率 | 耗时 | 说明 |
|---|---|---|---|
| `orders` | 每 15 分钟（对齐整刻），跳过 18:55–19:45 | 约 30 秒 | 吉他订单全量快照 + 变更事件 |
| `history` | 每天 19:10 起每小时一次，成功即停（最多 5 次） | 约 40 分钟 | 15216 个物品的成交历史 |
| `sde` | 每周日 09:30 | 3–5 分钟 | 静态数据包，约 95MB 下载 |
| `monthly` | 每月 1 日 04:30 | 1–2 分钟 | 历史数据月度聚合 + 压缩 |

**关键约束**：

- 内存上限 **300MB**（cgroup `MemoryMax`），SQLite 页缓存 `DB_CACHE_MB=32`
- ESI 令牌桶 `12000 / 15 分钟`，一轮订单约 836 → 占用 7%
- 数据目录 `$APP/data/`，6 个独立 SQLite 文件，稳态约 **0.5GB**

**任务之间严格串行**：同一时刻只会跑一个采集，天然避免抢 ESI 额度。

**当前部署状态**（2026-11-26 上线）：全新空库，首轮写入 418,146 单、用时 38.6 秒、
峰值 RSS 96MB；`data/eve_market_orders.db` 约 90MB；健康检查 cron 已装（每 10 分钟）。

## 3. 启动与停止

### 3.1 日常启停

```bash
sudo systemctl start   eve-controller
sudo systemctl stop    eve-controller      # 优雅停止，等当前任务收尾
sudo systemctl restart eve-controller
sudo systemctl disable eve-controller      # 只取消开机自启，当前进程不动
sudo systemctl enable  eve-controller
```

`stop` 的耗时：控制器收到 SIGTERM 后不再派发新任务，把 SIGTERM 发给当前子进程所在的**进程组**，10 秒仍未退出才 SIGKILL。正常 1–2 秒，**最坏约 12 秒**。unit 里的 `TimeoutStopSec=60` 只是兜底。

### 3.2 停止时正在跑的那一轮会怎样

**停止永远是安全的，最坏结果是「少采一轮」。**

| 数据 | 结果 |
|---|---|
| 订单主表 `market_orders` | **不变**。只有完整快照通过五道校验后才会更新，中途停止等于这一轮没发生 |
| 暂存表 `market_orders_staging` | 留下已提交的页（每 20 页提交一次），下一轮开头自动清空，不用手工收拾 |
| 变更事件 `market_order_events` | **不会多出假事件**。diff 没执行过就一条都不写 |
| `state.json` | 该轮记 `exit_code=-15`、连败 +1，只影响状态显示，不影响下次调度 |

### 3.3 停机久了会不会漏数据

不会漏掉能补的。`next_run_ts` 存在 `state.json` 里，重启后只要求值已过期，下一个 tick（≤10 秒）就立刻执行，不用等下个对齐点。

**补不回来的两块**：

- 订单表只保留最新快照，停机期间的历史快照 ESI 不提供
- `events` 是 **120 小时滚动窗口**，停超过 5 天，前面的窗口已经滚掉了

这是数据源的上限，不是配置问题。

## 4. 只暂停某一类采集（不停服务）

改 `$APP/controller.json` 里对应任务的 `"enabled": false`，然后**只给主进程**发 HUP：

```bash
sudo systemctl kill -s HUP --kill-who=main eve-controller
```

运行中的那一轮不受影响，之后不再触发。恢复时改回 `true` 再发一次。

> **必须带 `--kill-who=main`。** `systemctl kill` 默认发给 cgroup 内所有进程，正在跑的采集子进程没有 SIGHUP 处理器，收到就是直接终止，一轮采集白跑。

三种「停」的区别：

| 做法 | 效果 | 适用场景 |
|---|---|---|
| `systemctl stop` | 控制器和所有采集都停，重启后按 `state.json` 恢复调度 | 换代码、改 unit、腾内存 |
| `enabled: false` + HUP | 只停这一个任务，进程还在，其他任务照常 | 临时不想要某一类数据 |
| `systemctl disable` | 只取消开机自启，当前仍在跑 | 计划内长期关停 |

## 5. 更新代码

### 5.1 先对表：改了什么决定要做什么

| 改动文件 | 需要的动作 | 原因 |
|---|---|---|
| `collectors/*.py`、`runners/*.py`、`scripts/*.py`、`database_manager.py` | **什么都不用做** | 每次任务都是新起子进程，下次触发自动加载新代码 |
| `controller.json` | `systemctl kill -s HUP --kill-who=main` | 热重载调度表，运行中的任务不受影响 |
| `controller.py`、`core/`、`plugins/`、`paths.py`、`monitor.py`、`state.py` | `restart` | 属于控制器进程内的模块，只能重启 |
| `eve-controller.service` | `cp` → `daemon-reload` → `restart` | **三步缺一不可** |
| `logrotate-eve` | `cp` 即可 | logrotate 每次运行都重读配置 |

### 5.2 常规流程

```bash
cd /home/admin/eve_helper
git pull

# 只有改动了 unit 文件时才需要这两行：
# sudo cp eve-controller.service /etc/systemd/system/
# sudo systemctl daemon-reload

sudo systemctl restart eve-controller
journalctl -u eve-controller -n 30 --no-pager
```

> **不要用 `systemctl reload` 去加载 unit 改动。** 它发的是 SIGHUP，只让控制器重读 `controller.json`，跟 systemd 的 unit 缓存毫无关系。
>
> **为什么 unit 必须 `daemon-reload`**：systemd 在内存里缓存 unit 的解析结果，`cp` 只改磁盘文件。只 `restart` 会用**缓存里的旧定义**重启，改了 `Environment=` / `MemoryMax=` 也不生效，而且日志里一个字都不提。

**改过 SQL 的更新，务必在服务器上先跑测试再 restart**：

```bash
cd /home/admin/eve_helper
for f in tests/test_*.py; do printf '%-42s ' "$f"; .venv/bin/python "$f" 2>&1 | tail -1; done
```

服务器 SQLite 是 **3.26**，比开发机旧。`UPDATE ... FROM`（3.33+）、`RETURNING`（3.35+）、
`VACUUM INTO`（3.27+）在本地能过，在服务器会直接报 `near "FROM": syntax error`，
让整轮采集失败。

### 5.3 改完 unit 后确认生效

```bash
systemctl show eve-controller -p Environment -p MemoryHigh -p MemoryMax
systemctl cat eve-controller | head -5
```

期望：

```
Environment=PYTHONUNBUFFERED=1 PYTHONUTF8=1 TZ=Asia/Shanghai DB_CACHE_MB=32
MemoryHigh=209715200
MemoryMax=314572800
```

`DB_CACHE_MB` 不在里面，说明 `daemon-reload` 没做成功。

### 5.4 回滚

```bash
git log --oneline -3
git reset --hard <上一个 commit>
# 若同时回滚了 unit：
# sudo cp eve-controller.service /etc/systemd/system/ && sudo systemctl daemon-reload
sudo systemctl restart eve-controller
```

## 6. 手动补跑某个任务

```bash
sudo systemctl stop eve-controller                  # 先停，避免和计划任务抢同一张暂存表
cd /home/admin/eve_helper
.venv/bin/python controller.py --once orders
sudo systemctl start eve-controller
```

`--once` 会照常过闸门（资源、时间窗、每日成功判定都生效）、照常写 `state.json`，退出码就是子进程退出码（负值按 POSIX 惯例映射成 `128+n`，如 143 = 被 SIGTERM）。**两个坑**：

1. **它不拿 pidfile 锁**，服务在跑时也能执行。但同一个采集器绝不能和计划中的同名任务重叠——两边会同时写 `market_orders_staging`，两份快照互相污染。`--once sde` 这种不冲突的可以随时跑。
2. **别用 Ctrl-C 打断**。子进程是独立会话（`start_new_session=True`）起的，Ctrl-C 只杀控制器，采集进程会变孤儿继续跑到结束。真要中断：`pgrep -af _once.py` 找到 PID 再 `kill`。

## 8. 退出码与处置

| 码 | 含义 | 严重度 | 处置 |
|---|---|---|---|
| 0 | 成功 | — | 无 |
| 1 | 未预期异常 | 中 | 看 `logs/collectors/<task>.log` 末尾的 traceback |
| 2 | 快照不完整，保留旧数据 | 低 | 偶发（跨缓存刷新）会自动重拉；连续出现查网络 |
| 3 | 未取到订单 | 低 | 通常是 ESI 抖动或维护，下一轮自动恢复 |
| 4 | 写库被拒（规模骤降 / 重复） | **中** | 连续出现说明 ESI 数据异常或本地库有残留，见 9.6 |
| 5 | 历史错误超预算（>20% 的 type 失败） | 中 | 查 `history.log` 里的 HTTP 状态分布 |
| 6 | 今日历史数据尚未刷新 | **正常** | 维护延迟，后续整点会自动重试，无需处理 |
| -9 | 超时被终止 | 中 | 见 9.5 |
| -15 | 控制器停止时终止 | 正常 | 人工停服导致，不影响重启 |

## 9. 常见故障处置

### 9.1 服务起不来

```bash
systemctl status eve-controller --no-pager
journalctl -u eve-controller -n 50 --no-pager
```

按顺序排查：

1. **提示找不到单元** → 漏了 `sudo systemctl daemon-reload`
2. **路径不对**（`WorkingDirectory` / `ExecStart` 指向别处）→ `systemctl cat eve-controller` 对照实际目录
3. **`config.json` 缺失或 JSON 语法错** → `.venv/bin/python -c "import json;json.load(open('config.json'))"`
4. **venv 不存在或依赖缺失** → `ls .venv/bin/python`，没有就重建：

   ```bash
   python3 -m venv .venv
   # 直连 PyPI 会超时，先配镜像
   mkdir -p ~/.config/pip
   printf '[global]\nindex-url = https://mirrors.aliyun.com/pypi/simple/\ntimeout = 30\n' > ~/.config/pip/pip.conf
   .venv/bin/pip install -r requirements.txt
   ```
5. **`已有控制器在运行（pid=...）`** → 前台还留着一个实例，`pgrep -af controller.py` 找到后停掉，或删掉过期的 `.controller.lock`

### 9.2 任务一直显示「跳过」

`--status` 的备注列会直接写原因：

| 备注 | 原因 | 处置 |
|---|---|---|
| `闸门 resources：可用内存 150MB < 阈值 180MB` | 内存不足 | `free -m` 看谁占了；必要时把 `DB_CACHE_MB` 降到 16 后重载 unit |
| `闸门 resources：可用磁盘 1024MB < 阈值 2048MB` | 磁盘不足 | `du -sh $APP/data/*`，清理备份或旧日志 |
| `闸门 resources：load1 3.5 > 4.0` | 负载过高 | `top` 看是否有其他进程；本服务自身不会造成高负载 |
| `闸门 daily_success：今日 19:00 后已成功完成（19:52）` | 历史任务今天已完成 | **正常**，不用管 |
| `闸门 time_window：处于维护窗口 18:55-19:45` | 落在维护窗 | **正常**，窗口结束后自动恢复 |

### 9.3 遇到 420 / 429

- **429**：令牌桶打满。响应带 `Retry-After`，代码会自动退避，不用干预；反复出现说明并发或重试过高。
- **420**：**全局**错误限制被打穿（60 秒内超过 100 个非 2xx 响应），此时所有端点都返回 420。

处置：一般等 1–2 分钟自愈。要确认是不是我们的问题：

```bash
grep -cE " 4[0-9][0-9] " $APP/logs/collectors/orders.log
journalctl -u eve-controller --since "-30 min" | grep -E "420|429"
```

如果反复触发，临时把 `orders` 停掉（`enabled: false` + HUP），观察 `history` 是否在刷 404。

### 9.4 history 当天没跑成功

先看状态表里 `history` 的退出码：

- **6**：数据还没刷新（维护延长）→ **正常**，下一个整点会重试，最晚 23:10
- **5**：错误率过高 → 看 `history.log` 里的状态码分布
- 当天 5 次全失败 → 不用手工补，**次日采集会拿到完整历史**（ESI 返回的是连续区间），不会留空洞

### 9.5 任务超时（-9）

`orders` 超时 600s、`history` 超时 7200s。超时基本只有两种原因：

- 网络到 ESI 变慢（`ping`/`curl` 单页看耗时）
- 页面参数变了（日志里页数暴涨）

超时会被强杀，本轮作废，不影响下一轮。连续超时要查链路，不要简单调大 timeout。

### 9.6 连续出现退出码 4（写库被拒）

表示新快照的规模比库内低 10% 以上，或检出了重复订单，系统主动拒绝覆盖。可能是：

- ESI 真的出了数据问题（概率低，通常几分钟恢复）
- 本地库里有上一轮的残留（例如手工跑过 `--once` 与服务重叠）

确认后清空重建基线：

```bash
sudo systemctl stop eve-controller
sqlite3 $APP/data/eve_market_orders.db "DELETE FROM market_orders; DELETE FROM market_order_events; DELETE FROM market_order_snapshots;"
sudo systemctl start eve-controller
```

> 清空后第一轮是「全量插入 + 零 delete 事件」，这是正常的基线重建。

### 9.7 磁盘涨得快 / 内存不够

- `events` 表是 **120 小时滚动窗口**，稳态 330–420 万行、约 200MB，**不会无限增长**
- 文件不会自动缩小（只有每月 1 日的 `monthly` 任务对 history 库做 `VACUUM`），属正常现象，不用管
- 内存紧张时，把 unit 里的 `Environment=DB_CACHE_MB=32` 降到 `16`，然后 `cp` + `daemon-reload` + `restart`

## 10. 巡检

### 10.1 自动健康检查

```bash
bash /home/admin/eve_helper/healthcheck.sh
```

检查四项：服务是否 active、`--status` 能否读取、可用磁盘（阈值 2048MB）、可用内存（阈值 180MB），外加近 60 分钟控制器告警条数。退出码 0 正常 / 1 有异常。

建议加进 cron（每 10 分钟）：

```cron
*/10 * * * * /home/admin/eve_helper/healthcheck.sh >> /home/admin/eve_helper/logs/health.log 2>&1
```

> `healthcheck.sh` 用 `journalctl` 统计告警，需要用户在 `systemd-journal` 组里，否则告警数恒为 0（不报错，但会误报「无告警」）：`sudo usermod -aG systemd-journal admin`，重新登录生效。

### 10.2 每日一眼（1 分钟）

```bash
cd /home/admin/eve_helper && .venv/bin/python controller.py --status
```

关注三点：`orders` 连败为 0；退出码为 0；下次运行时间是 15 分钟内的整刻。

### 10.3 每周一次（5 分钟）

| 检查项 | 命令 | 期望 |
|---|---|---|
| 健康检查结论 | `bash healthcheck.sh` | 结论：正常 |
| events 规模 | `sqlite3 data/eve_market_orders.db "select count(*) from market_order_events;"` | 330–420 万 |
| 订单数 | `sqlite3 data/eve_market_orders.db "select count(*) from market_orders;"` | 40–45 万 |
| 磁盘 | `df -h /home` | 使用率 < 70% |
| SDE 是否成功 | `--status` 里 `sde` 的上次时间 | 最近一个周日 |
| 日志有无 420 | `grep -cE " 420 " logs/collectors/*.log` | 0 或极少 |

## 11. 应急操作

### 11.1 立刻止血（怀疑在拖垮机器 / 疯狂刷 ESI）

```bash
sudo systemctl stop eve-controller
pgrep -af "controller.py|_once.py" || echo "已全部退出"
```

停服不影响已有数据，恢复用 `start`。

### 11.2 只停订单，保留历史采集

改 `controller.json` 里 `orders.enabled = false`，然后：

```bash
sudo systemctl kill -s HUP --kill-who=main eve-controller
```

### 11.3 数据备份（在线，一致快照）

**不要直接 `cp` 正在写的 `.db`**（WAL 模式下会拿到不一致的副本）。用 SQLite 的 `.backup`：

```bash
mkdir -p /home/admin/backup
cd /home/admin/eve_helper
for db in eve_market_orders eve_market_history eve_items eve_universe; do
  sqlite3 data/$db.db ".backup /home/admin/backup/$db-$(date +%F).db"
```

单个文件也可以只备一个：

```bash
sqlite3 data/eve_market_orders.db ".backup /home/admin/backup/orders-$(date +%F).db"
```

备份体积与源库相当（orders 约 300MB），**注意别把 27G 磁盘塞满**，建议只留最近 2–3 份。

> 服务器的 SQLite 是 3.26（`sqlite3 --version` 实测 3.26.0），**不支持 `VACUUM INTO`**
> （需要 3.27+），所以只能用 `.backup`。它同样是在线一致快照，不需要停服。

## 12. 关键参数位置

| 参数 | 位置 | 现值 | 改完要做什么 |
|---|---|---|---|
| 订单间隔 | `controller.json` → `orders.schedule.minutes` | 15 | HUP |
| 维护窗跳过 | `controller.json` → `orders.skip_windows` | 18:55–19:45 | HUP |
| 事件保留时长 | `controller.json` → `orders.env.EVE_RETENTION_HOURS` | 120 | HUP（下一轮生效） |
| 历史重试时段 | `controller.json` → `history.schedule.expr` | `10 19-23 * * *` | HUP |
| 资源闸门阈值 | `controller.json` → `resources` / 各任务 `guards` | 内存 180MB、磁盘 2048MB、load 2.0×核数 | HUP |
| SQLite 页缓存 | `eve-controller.service` → `Environment=DB_CACHE_MB` | 32 | cp + daemon-reload + restart |
| 内存上限 | `eve-controller.service` → `MemoryHigh` / `MemoryMax` | 200M / 300M | 同上 |
| ESI 兼容日期 | `config.json` → `compatibility_date` | 2026-08-18（模板值） | 下一轮生效（无需重启） |
| UA 联系邮箱 | `config.json` → `user_agent` | 必须填真实邮箱 | 同上 |

`config.json` 里还有一段 `market_orders_tracker`，**对控制器不生效**——控制器走
`runners/orders_once.py` 的流式入口，变更事件总是产生，保留时长由
`controller.json` 的 `EVE_RETENTION_HOURS` 决定。那段只在单独运行采集器脚本时有用，不用改。

## 13. 不要做的事

1. **不要在服务运行时手动跑同名任务**（`--once orders` 与计划中的订单轮撞车会污染暂存表）。
2. **不要用 `systemctl reload` 加载 unit 改动**——它只让控制器重读 `controller.json`。
3. **不要把订单间隔改到 5 分钟以下**——ESI 的缓存 `Expires` 是 5 分钟，提前请求会被视为绕过缓存，可能被封。
4. **不要 `cp` 正在写的数据库文件**做备份，用 `.backup`。
5. **不要 `kill -9` 控制器**——子进程会变孤儿继续跑；用 `systemctl stop`（SIGTERM）。
6. **不要手工改 `state.json` 的 `next_run_ts`** 来「立刻跑一次」，用 `--once`。
7. **不要照抄 `config.collector.example.json` 的 `user_agent`**（`your-email@example.com` 是占位符，会覆盖内置的真实邮箱）。
